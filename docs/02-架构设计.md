# 02 架构设计

> 承接 [01-项目方案](01-项目方案.md)。本文回答：架构分层如何落时空公理、技术选型如何由时空需求推导。

## 1. 架构总览

| 层 | 组件 | 语言/域 | 空间职责（存什么） | 时间职责（怎么跑） | 规则职责（拦什么） |
|---|---|---|---|---|---|
| 运行时（时空管家） | host | Rust | 内核实例、插件句柄 | 装配顺序：memory→llm→tools→assets→agent-loop；REPL/单轮 | spawn 失败即退出；provider 探测前置 |
| 内核 | agent-kernel | Rust 库 | 插件注册表 | Envelope 路由、deadline 转发 | capability/manifest 校验、域隔离 |
| 流转-编排 | agent-loop | Rust / InProcess | 无跨调用可变态（状态在局部变量 + memory） | ReAct 状态机：感知→规划→行动→观察→回跳 | 保留名路由（`load_skill`）；软依赖降级 |
| 能力-模型 | llm-adapter | Python / Process | provider pack 注册表（无状态） | 请求级管道：选 pack→适配→归一化 | pack 形状不符注册期即失败 |
| 能力-行动 | tools | Python / Process | 工具注册表（常驻） | list 过滤 → call 分发 → 异常回喂 | WORKSPACE_ROOT 越界拦截；scope allow/deny |
| 能力-知识 | assets | Python / Process | skills/prompts 文件缓存 | 扫描→缓存→list/load | frontmatter 两字段校验 |
| 数据存储 | memory | TS / Process | 内存 Map + 每会话 JSON 文件 | 请求级读写 | 会话 id 文件名防穿越 |

**依赖铁律（时空防越界）**：Process 域 guest 之间物理不可见（内核域隔离），一切跨插件流转由 agent-loop 中转；guest 只依赖 `agent_kernel.guest` 运行时（规则防穿透）。

## 2. 技术选型推导（每条选型对应时空需求）

| 选型 | 时空需求 | 被否决的替代方案及原因 |
|---|---|---|
| 内核保持 agent-kernel，不动 | 空间隔离（进程域）、时间调度（deadline 转发）、规则校验（capability）已由内核物理保证 | 自研编排：重复造时空管家，且丢失契约校验 |
| provider 做单 guest 内 pack，不做每供应商一进程 | 变体是协议差异，共享归一化运行时；省 3 个 Python 进程的空间成本 | 每供应商一 guest：无状态插件无隔离收益；需独立生命周期时按同一 `base.py` 协议升级，契约不变 |
| skills+prompts 合一 assets 插件 | 两者本质同为「markdown 文件注册表」，时间行为同为扫描→缓存→读 | 分两插件：多付一个进程，无额外规则边界 |
| 工具集 7 件、纯 Python stdlib（可选 `ddgs`） | 空间：零重依赖、每工具 ~100 token 描述预算；时间：bash 覆盖 calculator/time 的语义 | 保留 calculator/current_time：占工具 token 且 bash 可覆盖；引 MCP：启动全量加载烧上下文（pi 立场） |
| 免费搜索链：区域选路（cn：Bing→搜狗→百度 HTML 零 key 直连；global：ddgs→DDG→Bing）+ key 服务自动提升 | 国内环境零 key 即可用（吸收国内零 key MCP 生态的引擎链共识）；多引擎故障转移保证时间流不断；不绕验证码（合规底线） | 引 MCP 搜索服务：多付进程/协议层且我们内核插件体系已覆盖同等能力；首选 Brave/Google：需 key 且大陆不可达 |
| 文件越界拦截在 tools 内部实现 | 规则契约的运行时落点离空间操作最近（拦截点=操作点） | 独立 sandbox 插件：Phase 1 过度设计；bash 进程沙箱留 Phase 2 宿主层（fail-closed，不谎称受限） |
| `load_skill` 由 agent-loop 保留名路由 | Process guest 无法互调（内核物理约束），agent-loop 是唯一 InProcess 编排者 | skills 暴露为普通工具：tools guest 无法调 assets guest，做不到 |
| 可追溯用 memory 第二 capability `session.trace`（Phase 3） | 可追溯=只追加系统事实（面向审计/恢复），记忆=模型上下文（可压缩重组）——不同关注点、同一持久化域，不新开进程 | 独立 trace 插件：多付进程无额外规则边界；与 dsh 一致地「从事件日志派生模型可见消息」 |

## 3. 执行流类型（全局唯一主循环 + 局部管道）

- **全局**：REPL 顺序管道（读入→turn→回显）；
- **核心**：agent-loop **状态机循环**（`max_rounds` 上限 + 末轮去工具强制收敛）；
- **插件内**：全部为请求级顺序管道，无事件循环、无常驻线程——Serial 语义下无并发可变态。

## 4. 部署与运行形态

单宿主进程 + 4 guest 子进程（memory/node、llm/python、tools/python、assets/python），配置全走环境变量（内核 Init 不传业务配置，子进程继承 env）。离线默认 mock provider，全链路可测试。
