# react-agent 生产级增强方案

> 运行模式：**生产**。文档树：[01-项目方案](01-项目方案.md)（总纲）｜[02-架构设计](02-架构设计.md)｜[03-模块设计](03-模块设计.md)（契约全集）｜[04-llm-adapter](04-llm-adapter-四层设计.md)｜[05-tools](05-tools-四层设计.md)｜[06-assets](06-assets-四层设计.md)｜[07-agent-loop](07-agent-loop-四层设计.md)。
> 定位：基于 agent-kernel 内核开发的生产级 ReAct agent。本方案在原架构（内核 + 插件 + 四条线契约不变）之上，回答三个问题并给出实施方案：
> ① 是否需要 skill / prompt 等插件？② 内置工具如何替换为生产级基本工具集？③ 免费联网搜索如何实现（对标 pi / DeepSeek Harness）？

---

## 一、项目目标

1. **插件体系完整化**：LLM 供应商 pack 化、skills 插件（开放标准 SKILL.md + 渐进式披露）、prompts 插件（可定制系统提示词），新增能力不改内核与编排层。
2. **工具生产级化**：去掉演示型工具（calculator / current_time / http_get），替换为文件操作 + bash + 联网搜索/阅读的生产级基本工具集，全部**免费可用（默认无 key）**。
3. **守住极简**：对齐 pi 的哲学——核心工具少而精，一切额外能力皆插件；固定契约（essence），灵活实现（form）。

## 二、本质定义（时空契约校验）

**本质**：一个以 agent-kernel 为时空管家的生产级 agent 运行时——内核管隔离与路由，能力全部下沉为插件，编排层只做 ReAct 状态机。

- **空间契约**：每个 guest 插件持有自己的状态空间（memory 的会话文件、tools 的工具注册表、assets 的技能/提示词文件缓存）；跨插件通信只走 `HostApi::call_plugin`，无共享内存。
- **时间契约**：主执行流为**状态机循环**（感知→规划→行动→观察→回跳），收敛于最终答案或 `max_rounds`；每个插件内部为请求级顺序管道。
- **规则契约**：跨插件靠 manifest capability + 线契约（编译期 Rust / 注册期内核拦截）；工具层靠 workspace 路径越界拦截（运行时拦截）；skill 激活靠保留工具名路由（编排层拦截）。

### 本质竞品锚定

| 竞品 | 本质定义（推断） | 与本项目差异 | 借鉴点 |
|---|---|---|---|
| pi | 极简编码 harness：4 工具 + <1000 token 提示词，其余全靠扩展 | 面向终端编码；TS 单进程 | 工具极简预设、SYSTEM.md 覆盖、skill 开放标准、扩展生态 |
| DeepSeek Harness | 一切皆插件的执行框架：可换 Loop、分层工具暴露、事件日志、沙箱 | 面向长任务；机制更重 | 模型可见 Schema 与运行时实现分离、scope allow/deny、提示词约束≠执行边界（fail-closed）、只追加事件日志实现全程可追溯 |
| opencode (SST) | client-server 编码代理：持久后端 + 多客户端，75+ provider 经 Models.dev 目录归一 | TS 单语言进程内插件；无内核级隔离 | Provider 归一化思路同构；工具集（read/write/edit/glob/grep/bash）对位；SQLite 会话持久化 |
| Hermes-agent (NousResearch) | 单核多入口个人 agent（CLI/Gateway/TUI），toolset 分组 + skills + SQLite(FTS5) 状态 | Python 单体；provider 三 API 模式进程内路由 | **「窄腰」哲学**（核心工具每次调用都付 schema 成本，能力放边缘）；toolset 平台预设；上下文压缩与 prompt caching |
| **本项目** | 内核级多语言插件 agent：进程隔离 + 契约路由 | **插件即进程**（内核保证），跨语言天然隔离 | — |

## 三、架构总览（第 0 级映射）

装配顺序：`memory → llm-adapter → tools → assets → agent-loop`（agent-loop 对 assets 为**软依赖**：catalog 拉取失败不致命）。

| 时空层级 | 插件（guest） | 域 | capability | 职责 |
|---|---|---|---|---|
| 数据规范（规则） | agent-kernel | — | — | manifest / capability / 线契约 / 路由 |
| 运行时（时空管家） | host（Rust） | — | — | 装配、spawn、探测、REPL |
| 流转-编排（调度时空） | agent-loop（Rust） | InProcess | `agent.chat` | ReAct 状态机、提示词组装、保留工具名路由 |
| 能力-模型 | llm-adapter（Python） | Process | `llm.chat` | provider pack 注册表 + 协议归一化 |
| 能力-行动 | tools（Python） | Process | `tools.exec` | 生产级工具注册表 + scope + 越界拦截 |
| 能力-知识 | assets（Python，**新增**） | Process | `assets.registry` | skills / prompts 的文件注册表（渐进式披露） |
| 数据存储（空间） | memory（TS） | Process | `memory.session` | 会话消息持久化 |

**依赖铁律**：guest 之间互不可见（Process 域无 guest→host 回调），一切跨插件流转由 agent-loop（唯一 InProcess 编排者）中转——空间防越界由内核域隔离物理保证。

## 四、问题一：需要哪些插件？（插件体系规划）

**判定原则（skill 精神）**：插件按「运行时关注点」划分进程，按「变体维度」划分模块。同一运行时关注点的变体（如各家 LLM 协议）做成一个 guest 内的 pack，不为每个变体付一个进程的空间成本；不同运行时关注点（如知识资产 vs 行动工具）各自成插件。

| 插件 | 做不做 | 形态 | 理由 |
|---|---|---|---|
| **llm provider packs** | ✅ Phase 1 | 单 guest 内 pack（`providers/*.py` + registry 自动发现） | 变体维度是协议差异，共享归一化运行时；需独立生命周期时按同一协议升级为独立 guest |
| **skills 插件** | ✅ Phase 1 | 与 prompts 合为一个 `assets` guest，capability `assets.registry` | 两者本质相同（markdown 文件注册表）；skill 采用开放标准 SKILL.md + 渐进式披露 |
| **prompts 插件** | ✅ Phase 1 | 同上（`prompts.list` / `prompts.get`） | 系统提示词可定制（SYSTEM.md + 具名模板） |
| **subagent** | ✅ Phase 3 | 保留工具 `task`：以 `{parent}#sub-{n}` 全新 session 复用 agent.chat 全链路，仅回传最终答案；深度防嵌套（DepthGuard RAII，depth≥2 拒绝） | 等单 agent 稳定后再加，避免过早抽象；子会话独立记忆+事件日志，`subagent` 事件关联可追溯 |
| **compaction**（上下文压缩） | ✅ Phase 2 | memory 新增 `summarize` op（`COMPACT_TRIGGER`/`COMPACT_KEEP`，0=禁用） | dsh：压缩是独立可选能力，不焊进 Loop |
| **event log**（事件日志/可追溯） | ✅ Phase 3 | memory 插件第二 capability `session.trace`（只追加 JSONL） | dsh「Model-visible means logged」；**可追溯≠记忆插件**：记忆=模型上下文（可压缩重组，面向模型），事件日志=系统事实（只追加不可变，面向审计/恢复/重建），见 01 §四注 |
| **sandbox**（进程级沙箱） | ✅ Phase 2 | 宿主层 sandbox-run 助手（Windows SAFER 受限令牌），fail-closed | dsh：提示词约束≠执行边界，fail-closed；探测失败即把 bash 移出 TOOLS_ENABLED，绝不静默直跑 |
| **web 网关**（web 页面） | ✅ Phase 3 | **入口级 Frontend 组件**（trait Frontend 两实现：ReplFrontend / WebFrontend，host 按 `REACT_FRONTEND` env 装配，编译期可切换） | host 是组合根（装配插件+选择前端），不是可插拔能力；前端切换必伴随重启，热插拔无收益，故不付 guest 跨进程代价（guest 不可互调，网关需调 `agent.chat` + `session.trace`）。静态单页由网关伺服，**UI 定稿为 dsh 风格「事件流式会话」**：markdown 渲染的模型发言 + 可折叠工具调用卡片（命令/参数/耗时/结果）+ 轮次分隔 + 异常标红；UI 是事件日志的渲染器（刷新恢复=日志重放），SSE 从事件日志实时渲染（opencode client-server 模式对位） |
| MCP 客户端 | ❌ 不做 | — | pi 立场：启动即全量加载工具描述烧上下文；需要时用 bash 包 CLI + skill 文档按需加载 |

### Skills 插件设计（渐进式披露三级映射）

采用 Agent Skills 开放标准（`SKILL.md` = YAML frontmatter + Markdown 正文），与内核约束的映射：

| 标准阶段 | 本项目落点 | Token 成本 |
|---|---|---|
| Discovery（宣告） | chat 开始时 agent-loop 调 `skills.list`，仅取 name+description 注入系统提示词附录 | ~100/个 |
| Activation（激活） | 模型调用保留工具 **`load_skill(name)`** → agent-loop 按**保留名空间**路由到 `assets` 的 `skills.load`，返回全文（<5000 token 指引） | 按需 |
| Execution（执行） | SKILL.md 指引模型用**基础工具**（read_file / bash / glob）读 `references/`、跑 `scripts/` | 按需，零新增机制 |

> 关键约束化解：Process 域 guest 之间不能互调，因此 skill 激活由 agent-loop（唯一 InProcess 插件）做保留名路由（`load_skill` 不进 tools 插件），路由规则一条 if，无越界。

SKILL.md frontmatter 只解析 `name` / `description` 两个必需字段（手写解析，不引 PyYAML）；`skills/` 目录扫描，无 skill 时整个 assets 插件静默降级。

### 可追溯（事件日志）设计说明——它不是记忆插件（Phase 3 预研）

DeepSeek Harness 的「全程可追溯」靠**只追加的 SessionEvent 事件日志**实现：用户消息、回复、工具调用/结果、轮次/步骤、授权确认、上下文压缩全部作为事件落日志；模型可见消息从日志**派生**（Model-visible means logged）；崩溃恢复不删中间事件而是补记 `interrupted` 边界；JSONL/SQLite 双后端。

**与本项目 memory 插件的职责边界**：

| 维度 | memory（记忆插件） | session.trace（事件日志，Phase 3） |
|---|---|---|
| 服务对象 | 模型（上下文） | 人与系统（审计/恢复/重建） |
| 写入语义 | 可覆盖、可压缩、可裁剪 | **只追加、不可变** |
| 内容 | 会话消息（模型可见形态） | 全量事件（含被压缩掉的原始事件、轮次边界、授权记录） |

两者是不同运行时关注点下的同一持久化域 → 落为 memory guest 的**第二 capability**（不新开进程，与 assets 合一原则一致）。写入方为 agent-loop（Process guest 不可互调，仍由编排者中转）。

### Prompts 插件设计

- 缺省提示词内置于 agent-loop（现状保留为兜底）；
- 覆盖优先级：`AGENT_SYSTEM_PROMPT`（env）> `SYSTEM.md`（工作区文件）> `prompts/` 目录具名模板（`PROMPT=name` 选择）> 内置缺省；
- `prompts.list` / `prompts.get` 供 host REPL 后续做 `/prompt` 命令（Phase 1 仅 env/文件覆盖，REPL 命令 Phase 2）。

## 五、问题二：生产级基本工具集（替换现有内置工具）

对标 pi（read/write/edit/bash 四件套）+ dsh（Minimal 预设 bash + str_replace_editor）+ 联网双件，**去掉 calculator / current_time / http_get**（bash 的 `python -c` / `date` / `curl` 语义覆盖，且不再占工具描述 token）：

| 工具 | 参数 | 生产级要点 | 免费 |
|---|---|---|---|
| `read_file` | path, offset?, limit? | 大文件截断（默认 256KB）、行号范围 | ✅ |
| `write_file` | path, content | 强制落在 WORKSPACE_ROOT 内（realpath 前缀校验） | ✅ |
| `edit_file` | path, old_string, new_string, replace_all? | str_replace 语义；old_string 唯一性校验（不唯一报错并给计数） | ✅ |
| `list_dir` | path, glob? | glob 过滤、类型标注 | ✅ |
| `bash` | command, timeout_ms? | 超时上限 60s、输出截断（64KB）；Phase 1 无进程沙箱但**显式声明**（env 确认开启），fail-closed 不谎称受限 | ✅ |
| `web_search` | query, max_results? | **免费默认 DuckDuckGo**；后端链见下节 | ✅ |
| `web_read` | url | Jina Reader 免费转 markdown，失败回退本地直抓 | ✅ |

7 个工具，工具描述总预算 ≈ 700 token（对齐 pi 的极简哲学）。保留 `TOOLS_ENABLED=a,b,c` 做按会话裁剪（dsh 的 scope allow/deny）。

**文件越界拦截（规则契约的运行时落点）**：`write_file` / `edit_file` / `read_file` / `list_dir` 统一经路径规范化（realpath）+ `WORKSPACE_ROOT` 前缀校验，越界返回字段级错误（哪个路径越界、合法根是什么）。bash 的进程级边界 Phase 2 宿主层实现——**不静默放行也不谎报已沙箱**。

## 六、问题三：免费联网搜索怎么实现（pi / dsh 的做法）

**pi 本体不带搜索**，全部由生态扩展提供。社区扩展的共识做法：

| 后端 | 费用 | 角色（pi 生态实践） |
|---|---|---|
| **DuckDuckGo HTML 抓取 / `ddgs` 库** | 完全免费无 key | **默认后端**（pi-web-search、pi-search-hub 均如此；`ddgs` 为 pip 包，更稳） |
| Brave Search API | 免费档 2000 次/月，需 key | 有 key 时自动升级（`BRAVE_SEARCH_API_KEY`） |
| SearXNG | 自托管免费 | fallback 后端（`SEARXNG_URL`） |
| Jina Reader（`r.jina.ai`） | 匿名免费 | URL → markdown 阅读器（pi-search-hub 的 `web_read` 即此实现） |

**本项目实现**（`web_search` 后端链，吸收国内零 key MCP 生态的共识做法——它们的本质全是「HTML 抓取公开引擎结果页」，MCP 只是封装，我们以 tools 内部引擎链实现同等能力）：

```
SEARCH_REGION=cn（国内默认，全部零 key 直连）：
  Bing HTML → 搜狗 HTML → 百度 HTML → 字段级错误（附已试引擎 + 解决提示）
SEARCH_REGION=global（海外默认）：
  ddgs 库（可选依赖）→ DuckDuckGo HTML → Bing HTML → 字段级错误
有 key 时自动提升：BOCHA_API_KEY（付费）/ BAIDU_API_KEY（千帆每日 100 次免费）/ TAVILY_API_KEY（每月 1000 次免费）
```

**反爬纪律**（从 free-search-mcp 等项目的失败经验吸收）：不绕验证码/PoW（合规底线，该引擎挑战即降级下一引擎）；错误信息附**已试引擎列表**；每引擎带简单冷却限速。

`web_read`：优先 `https://r.jina.ai/<url>`（免费 markdown），非 200 回退本地直抓 + 去 HTML 标签（国内站点直抓天然可达）。全链路 15s 超时、结果截断 32KB，返回**带来源 URL**。Phase 2 可选垂直增强：CSDN/GitHub README 正文抓取（Open-WebSearch 的 fetchCsdnArticle/fetchGithubReadme 做法）。

## 七、线契约变更清单（其余四条契约逐字不变）

**新增 `assets.registry`**（`assets.chat` 风格同 tools）：
- `{"op":"skills.list"}` → `{"ok":true,"skills":[{"name","description"}]}`
- `{"op":"skills.load","name":str}` → `{"ok":true,"content":str}` | `{"ok":false,"error":{...}}`
- `{"op":"prompts.list"}` → `{"ok":true,"prompts":[{"name","description"}]}`
- `{"op":"prompts.get","name":str}` → `{"ok":true,"content":str}`

**tools.exec**：契约不变；`list` 返回的工具集替换为生产级 7 件（受 `TOOLS_ENABLED` 裁剪）。

**agent.chat**：响应增加 `steps`（逐轮工具名+耗时，Phase 1 只观测不持久化）。

## 八、模块递归四层（Phase 1 范围，带生命周期钩子）

## 十一、新环境变量汇总

| 变量 | 默认 | 说明 |
|---|---|---|
| `WORKSPACE_ROOT` | 进程 cwd | 文件工具越界拦截根（realpath 前缀校验） |
| `TOOLS_ENABLED` | 全开 | 逗号分隔白名单，如 `read_file,write_file,bash` |
| `SEARCH_REGION` | `cn` | cn（Bing→搜狗→百度零 key 直连）/ global（ddgs→DDG→Bing） |
| `SEARCH_BACKEND` | 自动 | 强制指定引擎：bing / sogou / baidu / ddgs / duckduckgo / bocha / baidu_ai / tavily |
| `BOCHA_API_KEY` / `BAIDU_API_KEY` / `TAVILY_API_KEY` | — | 可选升级搜索后端（百度千帆每日 100 次免费；Tavily 每月 1000 次免费） |
| `SKILLS_DIR` / `PROMPTS_DIR` | `<workspace>/plugins/assets/{skills,prompts}` | 资产目录 |
| `AGENT_SYSTEM_PROMPT` / `SYSTEM.md` / `PROMPT` | 内置缺省 | 提示词覆盖优先级从高到低：env > SYSTEM.md > 具名模板 > 内置 |
| `HISTORY_LIMIT` | 不限 | 每轮回传历史条数上限 |
| `COMPACT_TRIGGER` / `COMPACT_KEEP` | `40` / `10` | 上下文压缩触发阈值（0=禁用）/ 保留最近条数 |
| `BASH_SANDBOX` | `on` | on=sandbox-run 受限令牌助手（探测失败 fail-closed 移除 bash，绝不静默直跑）；off=显式豁免直跑 |
| `REACT_FRONTEND` | `repl` | 前端选择：repl / web |
| `WEB_ADDR` | `127.0.0.1:8710` | web 网关监听地址 |

## 十二、愿景

Phase 1 完成后，本项目成为「内核级 pi」：进程隔离强于 pi（跨语言插件物理隔离），极简程度对齐 pi（7 工具 + 渐进式 skill）。长期沿 dsh 的六面向演进：可换 Loop → 分层工具 → 动态上下文 → 事件日志 → 分层权限 → 多维验收，每一面都以插件增量接入，内核与线契约保持稳定。
