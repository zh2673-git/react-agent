01 · 本质定义

一句话说清三家是什么

抛开名词看实质：一家在做"地基"，一家在做"可嵌入的框架"，一家在做"官方底座"。定位不同，取舍自然不同。

🦀 react-agent

"地基之上盖楼"。内核（agent-kernel）是独立产品：只做三件事——开辟/隔离插件的空间、编排执行时间流、强制校验契约与权限。所有能力（LLM/工具/记忆/编排）全是插件，支持不停机热替换。

🥧 pi

"可二次开发的终端 harness"。不是产品，而是 runtime 框架：主程序刻意做薄，把 agent runtime 中最易变、最复杂的部分拆开；用 extensions / skills / provider 注册表让用户不 fork 也能改造行为。

🐋 DeepSeek Harness

"底座 + 积木"。Model × Environment：模型是灵魂，Harness 给 agent 理解环境、使用工具、持续工作的能力。模型/工具/技能/会话/沙箱/存储/循环/调度/UI 全部可替换。

02 · 时空 + 规则三维

核心差异：隔离强度、执行流、契约强制

这是本页最硬的一节。三家在"空间怎么隔离、时间怎么推进、规则谁来强制"上的选择，决定了它们在别处的所有取舍。

评分口径：1–5 分，基于公开资料与本页分析的主观综合评估，非官方数据。

🔑 一句话读图

react-agent 的"隔离强度 / 契约强制"拉满，但"生态规模 / 易用上手"最短——典型的内核型项目。

pi 的"生态 / 易用 / 会话上下文"最高，隔离最低——典型的生态型框架。

dsh 最均衡，可扩展性最突出——典型的官方平台型底座。

🪐 空间契约（隔离）

react-agent：内核级三档——InProcess / Wasm（线性内存 + 无网络）/ Process（独立进程自愈）。插件独享 PluginContext，跨插件零共享内存。

pi：单进程 TS，工具只 spawn 子进程执行 bash；明确不做沙箱，推荐 Docker/VM 兜底。

dsh：Node host + 浏览器 client 两半；插件是同进程 npm 包；沙箱是一个插件插槽（isolated）。

⏱ 时间契约（执行流）

react-agent：内核调度器 = 事件循环 Loop（4 条优先级泳道 + 背压）；agent 主循环本身是编排插件驱动，可替换。

pi：agent-core 的双层嵌套循环（outer turn / inner tool-call），事件驱动 + steering / follow-up 双队列。

dsh：Cordis 事件循环；Agent Loop 是插件插槽，改行为优先挂钩子而非 fork。

⚖️ 规则契约（强制力）

react-agent：三层契约 + 编译期硬约束——trait Plugin + ApiVersion（编译期）、kernel.wit/proto（唯一真源）、CapabilityGate deny-by-default（运行时门控）。

pi：TS 类型 + TypeBox schema 校验 + Hook（可 block）；无内核级权限门控。

dsh：插件契约（npm 包 + patch.yml）+ 配置驱动；强制力在框架/文档层。

05 · 取舍

没有免费的午餐：各自换来了什么、付出了什么

三家都是深思后的取舍，不存在"全都要"。

react-agent

换来

最强隔离（进程 / WASM）+ 编译期契约 + 跨语言混布 + 事务性热替换 + 可复用独立内核。

付出

① 运行时全在内核，本仓不可直接改；② 插件 = 进程，启动/通信开销大，生态起步慢；③ 单维护者，~13k 行自研。

pi

换来

极简哲学 + 生态易扩展 + 会话树 / 压缩成熟 + 上手极快（一行 createAgentSession）。

付出

① 单进程无隔离（作者自陈"不是沙箱"）；② 无 MCP / sub-agent（故意）；③ 改 Loop 需 fork。

DeepSeek Harness

换来

官方背书 + 插槽最全（含 UI）+ 配置热更新 + 60+ 插件生态 + 成本工程（缓存命中率）。

付出

① Node 同进程，隔离靠插件自觉；② rc.6 破坏性变更；③ 插件模型重，学习成本高。

06 · 结论

react-agent 的真实位置

唯一把"时空 + 规则"做成了独立可复用内核的项目

pi 赢在生态与易用——把 agent runtime 拆得干净，让二次开发"不 fork 也能改"； dsh 赢在官方背书与插槽广度——从模型到 UI 九类插槽，配置驱动； 而 react-agent 是三者中唯一把"空间隔离 + 时间调度 + 规则校验"下沉为独立内核的项目： 编译期契约（只依赖 sdk）、运行期能力门控（deny-by-default）、三档隔离（InProcess/Wasm/Process）、事务性热替换—— 这套能力 pi 没有内核可放，dsh 放在 JS 容器里做不了多语言强隔离。它的天花板最高，但当前最短的板是生态与高层 agent 能力（会话树 / 上下文）。

建议 01
把"内核 + 居民"讲成体系

pi/dsh 是"产品"，react-agent 是"运行时 + 居民"。把 agent-kernel（地基）与 react-agent（旗舰居民）的关系摆到 README 最前面——这是对外最清晰的差异化。

建议 02
补会话树（对齐 pi 高价值项）

memory 插件加 parentId / branch，是当前与 pi 差距最大、也最影响真实编码体验的一块，比继续加工具更值。

建议 03
落实居民升级纪律

内核可控的优势依赖版本纪律：把 RESIDENTS.md 的升级确认做进发版流水线，否则"地基优势"会退化为"版本漂移风险"。

免责：pi 与 DeepSeek Harness 的信息来自公开资料（GitHub 描述、白皮书导读、源码拆解文章）， 可能与最新版本存在出入；react-agent / agent-kernel 数据来自本机源码（v0.1.20 / 内核 v0.1.7）。 评分与结论为基于上述口径的主观分析，欢迎指正。
