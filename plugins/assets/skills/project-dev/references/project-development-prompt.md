# Vibe Coding 项目开发与解读（时空运行时版）

> 用 AI 完成软件项目的全流程：**正向设计（从零生成）** 与 **逆向解读（分析已有）** 双向贯通。本版本以 **“时空+规则”公理** 为底层硬锚，将“运行时/内核”作为第一性原理，确保方法论适用于任何语言（Rust/Python/Java/Go/TS）及任何形态（单体业务/OS内核/AI Agent框架）。
>
> **物理底层公理（不可绕过的铁律）**：
> 1. **空间（内存）**：所有数据和指令必须存放在可寻址的内存中。运行时负责开辟、布局、标记归属和回收。
> 2. **时间（执行流）**：CPU 或调度器按顺序、分支（跳转）、循环（回跳）三种基本结构推进指令指针。运行时负责编排和切换。
> 3. **规则（约束）**：类型系统、接口契约、权限沙箱定义了“内存里的 01 该如何被解读和操作”。运行时负责在编译期或运行期强制校验。
>
> **两种模式**：
> - **正向模式**：从需求出发，先定义“时空+规则”契约，再生成方案与代码。
> - **逆向模式**：从源码出发，先还原其隐含的“时空+规则”设计，再产出架构解读报告。


## 执行环境约定

| 职责 | Agent 环境（自动执行） | 网页端 LLM 环境（指引执行） |
|---|---|---|
| **文件产出** | 自动创建/修改文件 | 输出完整内容，标注目标路径，用户搬运 |
| **命令执行** | 自动执行（测试/构建/git 等） | 输出命令 + 预期结果，用户执行后回贴 |
| **版本管理** | 自动 git commit/revert | 输出判断 + 理由，用户自行操作 |
| **代码获取** | 自动 clone / 读取文件 | 引导用户提供源码或仓库地址 |
| **信息检索** | 自动搜索项目信息 | 输出搜索指令，用户回贴结果 |
| **测试验证** | 自动运行测试并采集结果 | 思考层推理，用户回贴测试结果 |
| **迭代触发** | 自动进入下一轮 | 完成一轮后等待用户触发 |

**核心纪律**：Agent 真实执行所有操作；网页端不假装执行，所有需环境操作的步骤输出指令，用户回贴后继续。

**模式选择**：
- **正向模式**：`program.md` 首行声明 `探索` 或 `生产`。探索模式仅产出精简方案和代码；生产模式产出完整文档树。
- **逆向模式**：无 `program.md` 要求，直接从代码挂载开始。
- **优化模式**：逆向解读的延续——审计结论沉淀为**模块级优化方案**，按方案迭代执行（见 §3.4）。


## 第0步：模式选择与上下文初始化

### 0.1 判断用户意图

| 用户输入特征 | 判定模式 |
|---|---|
| "我想做一个..."、"帮我设计..."、"从零开发..." | **正向模式** |
| "帮我分析这个项目..."、"解读一下..."、"这个代码怎么样..." | **逆向模式** |
| 提供了仓库地址 / 粘贴了完整源码 / 上传了代码文件 | **逆向模式** |
| "优化一下..."、"重构这个模块..."、"持续改进/修这个缺陷..."（针对已有项目） | **优化模式** |
| 不明确 | 反问用户："你是想从零设计一个新项目，还是想分析解读已有项目？" |

### 0.2 正向模式：上下文初始化

- **情况A（有 `program.md`）**：直接读取，按首行模式进入第1步。
- **情况B（无 `program.md`，用户仅提供自然语言需求）**：
  - AI **必须先充当"分析师"**，根据用户原始需求，生成一份《草稿版 `program.md`》。
  - 草稿必须包含：运行模式（让用户选）、项目目标、目标编程语言（让用户确认）、验证契约（P/Q/I 框架，具体值让用户填或确认）、修改范围、约束条件、研究方向（优先级1/2/3）。
  - **草稿中必须预留"时空契约"确认项**：要求用户确认核心数据的空间归属（谁独占/谁共享）和时间执行流类型（顺序管道/事件循环/状态机）。
  - 草稿生成后，**反问用户确认**："以上是我的理解，请确认或逐项修改。确认后我将正式进入方案设计阶段。"
  - **在用户明确确认之前，AI 不得进入第1步**。
  - 用户确认后，将草稿固化为正式的 `program.md`，再进入第1步。

### 0.3 逆向模式：代码挂载与信息采集

- **情况A（用户提供仓库地址）**：
  - Agent 环境：自动执行 `git clone <url>`，扫描目录结构，读取关键文件。
  - 网页端环境：输出指令 `git clone <url>`，要求用户执行后回贴目录结构和核心文件内容。
- **情况B（用户粘贴完整源码）**：直接接收，按文件拆分，标注每个文件的目标路径。
- **情况C（用户提供项目名称）**：
  - Agent 环境：自动搜索（如 GitHub 搜索、PyPI/CRAN/npm 等包管理器）。
  - 网页端环境：输出搜索关键词和平台，用户回贴搜索结果或自行提供源码。

**挂载完成后，AI 必须输出以下确认信息**：

```


## 一、物理公理与递归四层模型（唯一核心规则）

### 1.1 时空公理（所有编程的底层硬锚）

任何软件系统（无论多抽象）都必须在物理或虚拟硬件上落地为以下三者的组合：

| 公理维度 | 物理本质 | 在软件抽象中的体现 |
|---|---|---|
| **空间** | 内存（寄存器/堆/栈/文件/网络缓冲）中开辟的连续或离散地址块，用于存放数据和指令。 | 变量、对象、结构体、数据库表、文件块；Rust 的 Ownership（谁拥有这块空间）、C++ 的 malloc/new。 |
| **时间** | 指令指针（PC）在内存地址间的移动方式：顺序（PC+1）、分支（PC=目标地址）、循环（条件回跳）。 | 函数调用栈、事件循环（Loop）、状态机跳转、异步任务的调度队列；OS 的进程时间片。 |
| **规则** | 硬件 ALU 的运算规则 + 软件层附加的类型检查、权限校验、接口契约。 | 类型系统（整数/字符串不能混用）、Trait/Interface、沙箱隔离、编译时借用检查（Rust）。 |

**重要推论**：**运行时（Runtime/内核）就是"时空管家"** —— 它负责开辟空间（分配内存/注册资源）、编排时间（启动/调度/停止执行流）、并强制校验规则（拦截越界访问/类型错误/生命周期违规）。无论是 OS 内核、JVM、Node.js 事件循环，还是 Cordis 插件容器，本质上都在做这三件事。

### 1.2 递归四层模型（在时空公理上的建筑学映射）

任意粒度的代码单元（整个项目、模块、类/结构体、函数/方法）都遵循四层结构。当递归作用于不同层级时，四层自然映射为不同的物理形态。

| 四层结构 | 定义（对接时空公理） | 正向设计（从零） | 逆向解读（分析已有） |
|---|---|---|---|
| **数据规范** | 定义空间内的数据布局：类型、长度、枚举值、合法性约束（规则层的静态部分）。 | 设计属性/字段定义、常量、枚举。 | 提取实体类/结构体的字段、类型、注解、枚举值。 |
| **数据存储** | 数据空间的持久化或驻留方式：堆/栈/数据库/文件/缓存（空间的具体落地）。 | 设计数据库 Schema、内存缓存、文件格式。 | 识别 ORM、文件 IO、Redis 调用、内存状态保持方式。 |
| **数据流转** | 数据在时间轴上的变化轨迹：顺序计算、条件分支、循环迭代、事件驱动（时间的编排）。 | 实现业务逻辑、状态机、事件处理器。 | 追踪函数调用链、状态机转移、事务边界、事件发布/订阅链。 |
| **数据接口** | 外部访问该空间和触发时间流的固定入口（规则的对外暴露形式）。 | 设计对外公共方法、API 路由、CLI 命令。 | 提取对外暴露的公共接口、路由注册、RPC 方法签名。 |

**第0级（项目级）四层映射 + 运行时显式化（对接"时空管家"）**：

| 物理层级 | 对应目录（以 Rust/Python 为例） | 职责（明确时空职责） | 依赖规则（硬边界） |
|---|---|---|---|
| **数据规范（规则基座）** | `core/` | 全局配置、常量、错误码、DTO、类型定义、日志门面、数据库连接池抽象、外部 SDK 接口定义。 | ❌ 不依赖任何其他目录（纯规则定义）。 |
| **数据存储（空间落地）** | `infrastructure/` | 数据库连接实现、外部 API Client、文件 IO、消息队列 Producer/Consumer、Redis 操作。 | ❌ 不依赖上层业务（仅依赖 `core/` 的抽象接口）。 |
| **数据流转 - 核心规则（业务时空）** | `domain/` | 核心实体、业务规则、状态机、领域服务（"四层模型"的业务落地）。内部可包含 `entity/`、`event/`、`service/`。 | ❌ 不直接依赖基础设施（通过依赖注入接收 `infrastructure` 的接口）。 |
| **数据流转 - 编排（调度时空）** | `application/` | 用例编排、跨模块协调、事务管理（begin/commit/rollback）、事件发布/订阅的组装。 | ✅ 可依赖 `domain/`（实体）和 `infrastructure/`（通过接口）。 |
| **运行时/内核（时空管家）** | `runtime/` 或 `bootstrap/` | **显式管理生命周期**：`init()` 开辟全局空间（注册插件/服务）、`start()` 启动时间流（事件循环/调度器）、`stop()` 暂停、`destroy()` 按依赖逆序回收空间。**显式定义执行流模式**：是顺序管道、事件驱动 Loop，还是状态机 Jump。 | ✅ 可依赖所有层，但只负责"启动/停止/回收"，不写具体业务流转逻辑。 |
| **数据接口（时空入口）** | `interfaces/` 或 `api/` | REST API 路由、CLI 命令、消息队列消费端、WebSocket 端点。将外部触发（时间事件）转化为内部调用。 | ✅ 可依赖 `application/` 和 `runtime/`（获取调度句柄）。 |

**依赖方向铁律（时空防越界）**：
- **空间防越界**：`infrastructure` 绝不能反向依赖 `domain` 的具体实现（防止底层存储直接操作业务空间）。
- **时间防乱序**：`domain` 不能直接调用 `runtime` 的调度器，只能暴露事件或状态，由 `application` 编排后交给 `runtime` 驱动。
- **规则防穿透**：所有跨层访问必须通过 `core/` 定义的接口或 `interfaces/` 定义的契约，禁止直接操作非本层内存空间。

**递归展开规则**：
- **第0级（项目级）**：按上表自然生成或审计所有目录。
- **第1级（模块级）**：在 `domain/{module}/` 或 `application/{module}/` 下，继续按四层拆解该模块的实体、服务、接口。
- **第2级起**：强制锚定父本质，格式：`在"{父本质定义}"的时空约束下，本子模块的本质是……`。超过3层终止。
- **递归终点**：直到一个模块内部不再需要拆分子模块为止（通常是单一函数或纯数据结构）。


## 二、正向模式：形成方案（时空驱动设计）

### 2.1 从需求到方案的五步（嵌入时空契约）

```
第0步：上下文初始化（确认 program.md 存在）
第1步：是什么 —— 本质定义（必须通过时空契约校验）→ 本质竞品锚定 → 类归属 → 关键属性展开
第2步：为什么 —— 因果链（回溯物理底层）→ 技术选型推导（由本质+时空需求推导）
第3步：怎么做 —— 按第0级时空映射分配目录 → 递归深入核心模块 → 显式设计 runtime/ 生命周期钩子
第4步：时空契约验证 —— 人工或自动检查空间/时间/规则是否闭环
```

**本质定义的时空契约校验（新增硬性门槛）**：
在给出“本质定义”后，AI 必须自答以下三条，并写入 `01-项目方案.md`：
1. **空间契约**：该系统的核心数据（状态）由谁独占？何时分配（`init`）？何时回收（`destroy`）？是否存在跨边界共享（如 Arc/Rc）？
2. **时间契约**：主执行流是哪种形态？**顺序管道**（一个接一个）、**事件循环 Loop**（`while let Some(event)=rx.recv()`），还是**状态机跳转**（`match state { ... }` + 修改 PC）？
3. **规则契约**：越界访问（如插件想改内核数据）由谁拦截？编译时（Rust 借用检查）拦，还是运行时（JS Proxy / 权限校验）拦？

### 2.2 项目方案文档结构（生产模式）

```
docs/
├── 01-项目方案.md          # 目标 + 本质定义（含时空契约校验） + 竞品锚定 + 架构总览（含第0级映射+runtime/设计）+ 模块递归四层设计（必须含生命周期钩子）+ 验证方式 + 愿景
├── 02-架构设计.md          # 架构图 + 技术选型理由（必须说明选型如何满足时空需求）
├── 03-模块设计.md          # 模块划分 + 接口契约 + 执行流模式说明
├── 04-{模块A}-四层设计.md   # 每个核心模块的递归四层详细设计，标注 init/start/stop/destroy 钩子
└── ...（递归子模块同结构）
```

探索模式仅产出 `01-项目方案.md` 及代码。

## 三、逆向模式：形成解读报告（还原时空设计）

### 3.1 从源码到解读报告的六步

```
第0步：代码挂载与信息采集（已完成）
第1步：逆向本质定义 → 从代码反推系统本质，并还原其隐式的时空契约（空间归属、时间流形态、规则拦截点）
第2步：第0级分层审计 → 对照标准时空映射，评估目录结构与职责分配，重点检查 runtime/ 或调度器是否存在
第3步：执行流类型识别（新增）→ 识别主循环是顺序管道、事件驱动 Loop，还是状态机跳转
第4步：模块递归拆解 → 对核心模块逐层进行四层提取（规范/存储/流转/接口），并标注生命周期钩子的实际落点
第5步：依赖方向审计 → 检查是否违背时空防越界铁律
第6步：验证契约审计 → 提取现有测试，评估 P/Q/I 的实际覆盖与通过情况
```

### 3.2 解读报告文档结构（生产模式）

```
docs/
├── 01-项目解读报告.md          # 概览 + 本质逆向定义（含时空契约还原） + 执行流类型识别 + 第0级分层审计总表 + 验证契约审计 + 技术债务汇总 + 改进建议

### 3.4 优化模式（逆向解读的延续：按方案迭代执行）

逆向解读产出审计结论后，存量项目的持续优化按以下约定执行：

- **方案落点**：优化方案落在**模块目录内**（如 `crates/{module}/PLAN.md`），随代码走；`docs/` 编号序列属构建期快照，优化期**不新增**编号文档。
- **文档分层**：模块 `PLAN.md` = 演进轨迹（每轮重构更新：审计结论 / 路线 / 迭代记录）；模块 `README.md` = 对外契约（仅契约实际变更时同步最终形态，不写过程性进度）。
- **迭代循环**：Phase 1 更新 PLAN（目标/方案）→ Phase 2 代码 → Phase 3 测试（P/Q/I）+ 保留或回退决策 → PLAN 追加迭代记录。
- **失败归档**：评估过但不做的方案记入 PLAN「已评估不做」，避免后续重复尝试。
- **跨插件节奏**：插件化项目按"一个插件一个 PLAN"逐个优化，先修规则层（正确性），再修时间层（效率/健壮性），最后工程面收敛。

### 3.5 代码体量审计与超大文件拆分（优化模式扩展）

触发：用户要求评估文件是否过大/需要拆分，或迭代中发现单文件体量失控。按以下约定执行：

- **审计门槛（缺省参考，按项目调整）**：单文件 > ~800 行且内容跨多个域（职责混杂）→ 拆分候选；
  500–800 行多域混杂 → 观察；纯数据 / mock / 脚本化产物可豁免。**行数只是引子，域混杂才是依据**——
  内聚单一的 1000 行文件好过职责混杂的 600 行。
- **审计产出三清单**（沉淀进模块 PLAN.md「路线」）：

  | 清单 | 内容 | 目的 |
  |---|---|---|
  | 拆分 | 文件 + 行数 + 域混杂点 | 本轮执行 |
  | 不拆 | 文件 + 理由（内聚单一/契约面小/刚过阈值） | 锁定结论防反复评估 |
  | 缓拆 | 文件 + 触发条件 + 既定方案 | 收益<成本时挂起，条件到再动 |

- **拆分纪律（纯搬家，零逻辑改动）**：
  1. **按域内聚切，不按行数切**：以模块声明、分区注释、文件边界为切割线；移动时不顺手改逻辑。
  2. **契约兼容优先**：用 re-export/转发让外部调用路径零改动（Rust `pub use` 聚合导出、
     经典脚本按原序加载共享全局作用域、HTTP 路由表不动）。
  3. **执行顺序**：核心逻辑先行（编译 + 单测全绿再动下一处）→ UI/脚本殿后（语法检查 + 运行时回归）；
     单测随域迁移，测试路径即文档。
  4. **新语义边界显式验证（I 不变量）**：拆分会改变符号与资源的可见范围——经典多脚本的函数声明
     提升只在各自文件内生效（顶层**立即调用**的函数必须已在前序文件声明；回调内引用不受影响）、
     静态资源 serve 白名单/MIME 映射可能是编译期常量（新增文件需重编或走既有放行规则）、
     构建/脚本工具参数传递的隐式行为（如 PowerShell 数组传参拍平）。逐项列出并验证——
     这是拆分事故的主要来源，"行数守恒 + 语法通过"远远不够。
  5. **收尾**：PLAN.md 迭代记录；serve 文件集 / 调用路径等契约实际变更时同步两级 README
     （先模块后主表）；工具链踩坑入项目记忆。

## 七、完整示例（以“Cordis-like 插件内核”演示时空模型）

**用户需求**："我想做个 Rust 版的插件内核，像 Cordis 那样，支持动态插拔。"

**第0步草稿确认后，第1步本质定义（时空契约校验）**：

- **本质定义**：一个管理插件空间归属和时间调度的轻量运行时。
- **时空契约校验**：
  - 空间：每个插件持有自己的服务空间（Context），宿主通过 `Arc` 共享只读内核信息，插件间不能直接访问对方内存。
  - 时间：主执行流为事件循环 Loop（`while let Some(event)=rx.recv()`），插件注册 `on_event` 回调触发流转。
  - 规则：编译时通过 Trait 限定插件接口（`trait Plugin`），加载时校验符号。

**第0级映射**：

| 层级 | 目录 | 内容 |
|------|------|------|
| 规范 | `core/` | Plugin Trait, Context 接口, 错误码 |
| 存储 | `infrastructure/` | (预留) 持久化插件配置 |
| 流转-规则 | `domain/` | 插件实体、依赖图、状态机 |
| 流转-编排 | `application/` | 加载/卸载用例 |
| 运行时 | `runtime/` | **事件循环 Loop，调度器，生命周期钩子管理者** |
| 接口 | `interfaces/` | CLI 命令 |

**代码片段（runtime 显式生命周期）**：

```rust
// 文件：runtime/scheduler.rs
pub struct Runtime {
    plugins: Vec<Box<dyn Plugin>>,
    rx: mpsc::Receiver<Event>,
}

impl Runtime {
    // 空间开辟
    pub fn init(&mut self) {
        // 分配内核 Context
    }
    // 时间流启动（主循环）
    pub fn start(&mut self) {
        while let Some(event) = self.rx.try_recv() {
            self.dispatch(event);
        }
    }
    // 时间流暂停
    pub fn stop(&mut self) {
        // 停止接收新事件
    }
    // 空间回收（按依赖逆序 drop）
    pub fn destroy(&mut self) {
        self.plugins.reverse();
        self.plugins.clear(); // 触发 Drop
    }
}
```
